# 타입 검사를 통과한 코드가 런타임에 터졌다

우리는 흔히 타입 안전성을 위해 타입스크립트를 도입합니다.
하지만 타입스크립트의 타입 정보는 자바스크립트로 변환되는 과정에서 사라집니다.
타입 검사를 통과했다고 해서 실행 중인 값을 계속 검사해주는 건 아니죠.

그렇다면 타입 검사를 통과한 코드는 런타임에도 정말 안전할까요?
타입 체커는 값의 변화를 어디까지 따라갈 수 있고, 어디서부터는 우리가 직접 확인해야 할까요?

타입 좁히기를 따라가면서, 타입 체커가 확인해주는 것과 우리가 직접 살펴야 하는 것 사이의 경계를 이야기해보려고 합니다.

## 타입 검사는 통과했는데, 왜 에러가 날까요?

장바구니 코드로 예를 들어보겠습니다.

> 예제는 TypeScript 5.8.2에서 `strict: true`, `exactOptionalPropertyTypes: false`로 확인했습니다.
> 코드의 `^?` 주석은 바로 위 식별자의 추론 타입을 나타냅니다.

```tsx
interface Item {
  name: string;
  price: number;
}

interface Discount {
  amount: number;
}

interface Cart {
  items: Item[];
  discount?: Discount;
}
```

`discount`는 `items`로부터 계산해둔 할인 정보입니다.
매번 다시 계산하기는 아까우니 장바구니 객체에 저장해두는 형태죠.
아직 계산하지 않았거나 다시 계산해야 할 때는 `undefined`로 둡니다.

장바구니에 상품을 추가한 뒤, 할인 금액을 보여주는 상황을 생각해보겠습니다.
할인은 상품 구성과 주문 금액에 따라 달라지므로,
상품이 추가되면 기존 할인 정보를 비우고 다시 계산해야 합니다.

하려는 일은 간단합니다.
할인 정보가 있는지 확인하고, 새 상품을 추가한 뒤 할인 금액을 화면에 보여주는 것입니다.

**그런데 타입 검사를 통과한 코드가 할인 금액을 읽는 순간 에러를 내는 상황이 발생했습니다.**

타입 검사를 통과했는데 왜 에러가 날까요?

<br/>

`addItemAndShowDiscount`는 장바구니에 할인 정보가 있는지 확인 후 새 상품을 추가하는 함수입니다.
에러가 난 곳은 상품을 추가한 뒤에 할인 금액을 읽는 부분이었습니다.
원인을 찾기 위해 먼저 상품을 추가하기 전후의 타입부터 살펴보겠습니다.

```tsx
function addItemAndShowDiscount(cart: Cart, newItem: Item) {
  cart.discount;
  //   ^? Discount | undefined

  if (cart.discount) {
    cart.discount;
    //   ^? Discount

    addItem(cart, newItem); // 새 상품 추가

    cart.discount;
    //   ^? Discount
  }
}
```

처음에는 `Discount | undefined`였던 타입이 `if` 안에서는 `Discount`로 좁혀집니다.
값이 있는지 확인했으니 여기까지는 자연스럽습니다.

그런데 `addItem(cart, newItem)`를 호출한 뒤에도 타입은 여전히 `Discount`입니다.
타입만 보면 새 상품을 추가한 뒤에도 할인 정보를 그대로 읽어도 될 것 같습니다.

**하지만 값이 있다고 확인한 건 `addItem` 함수를 호출하기 전입니다.**

`addItem`이 실행되는 동안 `cart.discount`가 바뀌었다면 어떨까요?

<br/><br/>

## addItem 안에서는 무슨 일이 일어났나요?

`addItem`은 `cart`를 통째로 받았습니다.
호출하는 코드만 봐서는 함수 안에서 장바구니의 어떤 값을 바꾸는지 알 수 없습니다.

이런 구현도 얼마든지 가능합니다.

```tsx
function addItem(cart: Cart, item: Item) {
  cart.items.push(item);
  cart.discount = undefined; // 상품이 바뀌었으니 할인 정보를 다시 계산해야 함
}
```

`discount`는 `items`에서 파생된 값이니,
상품이 바뀌면 기존 할인 정보는 더 이상 유효하지 않기 때문에 그대로 써도 되는지 다시 확인해야 합니다.
이 구현에서는 상품이 추가될 때마다 할인 정보를 비워두고 다시 계산하도록 했습니다. 흔한 캐시 무효화 처리죠.

일부러 문제를 심어놓은 코드가 아니라, 계산해둔 값을 저장하는 객체라면 나올 법한 구현입니다.

이제 처음에 하려던 대로, 새 상품을 추가한 뒤 할인 금액을 읽어보겠습니다.
화면에 표시하는 대신 콘솔에 출력해봅시다.

```tsx
function addItemAndShowDiscount(cart: Cart, newItem: Item) {
  if (cart.discount) {
    cart.discount;
    //   ^? Discount

    addItem(cart, newItem); // cart.discount = undefined

    cart.discount;
    //   ^? Discount

    console.log(`${cart.discount.amount}원 할인이 적용되었습니다`);
    //                           ^? number
    // 타입 검사 통과. 런타임에는 TypeError
    // Cannot read properties of undefined (reading 'amount')
  }
}
```

이 함수를 실행하면, 할인 금액을 출력하려는 줄에서 `TypeError`가 발생합니다.

`if`에서 확인할 때는 분명히 `cart.discount`에 값이 있었습니다.
하지만 `addItem`이 상품을 추가하면서 할인 정보를 `undefined`로 비웠고,
그 상태에서 비어있는 값인 `.amount`를 읽으려 했기 때문에 에러가 발생합니다.

실제 값(`undefined`)과는 달리 타입 체커는 여전히 `cart.discount`를 `Discount`로 판단하므로
이 속성으로의 접근을 허용합니다.
앞에서 예고한 **“타입 검사는 통과했는데 런타임에서 터지는 상황”이죠.**

<br/>

여기서 이런 질문이 생길 수 있습니다.

> “`addItem` 안을 보면 `discount`를 지우는 게 보이는데, 타입스크립트도 알 수 있는 거 아닌가요?”

타입스크립트도 함수 본문을 검사합니다.

다만 일반적인 함수 호출에서는, 본문이 인자의 속성을 어떻게 바꾸는지까지 따라가서
호출부의 좁히기를 갱신하지는 않습니다.

함수 안의 코드가 타입에 맞는지 검사하는 것과, 그 함수가 바꾼 상태를 호출한 쪽에 반영하는 것은 별개의 일입니다.

<br/><br/>

## 함수 호출 뒤에 좁히기를 되돌리면 되지 않을까요?

함수 안에서 값이 바뀔 수 있다면, 호출할 때마다 좁혀둔 타입을 원래대로 되돌리면 어떨까요?

```tsx
cart.discount;
//   ^? Discount | undefined

if (cart.discount) {
  cart.discount;
  //   ^? Discount

  addItem(cart, newItem);

  cart.discount;
  //   ^? Discount
  // 만약 여기서 Discount | undefined로 되돌린다면?

  console.log(`${cart.discount.amount}원 할인이 적용되었습니다`);
}
```

그러면 이후에 `cart.discount.amount`를 바로 읽으려 할 때 타입 오류를 낼 수 있습니다.
앞의 런타임 에러를 미리 잡을 수 있는 거죠.

하지만 이 규칙을 모든 함수 호출에 적용하면, 값을 읽기만 하는 함수를 호출한 뒤에도 다시 확인해야 합니다.

```tsx
if (cart.discount) {
  logCart(cart);

  // logCart가 값을 바꿨을 수도 있으니 다시 확인
  if (cart.discount) {
    renderBadge(cart);

    // renderBadge가 값을 바꿨을 수도 있으니 또 확인
    if (cart.discount) {
      console.log(cart.discount.amount);
    }
  }
}
```

좁혀둔 값을 계속 쓰려면 함수 호출 뒤마다 같은 조건을 확인해야 합니다.
일명 타입 체크 지옥이죠.

그렇다고 값을 바꾸는 함수만 골라내기도 쉽지 않습니다.
호출한 함수가 직접 값을 바꾸지 않더라도, 그 안에서 부르는 다른 함수가 값을 바꿀 수 있습니다.
전달받은 콜백이나 같은 객체를 가리키는 다른 참조를 통해서도 변경이 일어날 수 있죠.

결국 함수 하나의 본문만 읽는 것으로는 충분하지 않습니다.
이어지는 함수 호출과 객체 참조까지 따라가려면 분석 범위와 복잡도가 커집니다.

타입스크립트 팀도 이 두 접근의 문제를 논의한 적이 있습니다.

[제어 흐름 분석의 트레이드오프 논의](https://github.com/microsoft/TypeScript/issues/9998)

> One option is to be *pessimistic* and reset all narrowings, assuming that any function might mutate any object it could possibly get its hands on. Another option is to be *optimistic* and assume the function doesn't modify any state. Both of these seem to be bad.

함수가 값을 바꿀 수 있다고 보고 좁히기를 모두 해제할지, 바꾸지 않는다고 보고 유지할지.
두 접근 모두 문제가 있다는 주장입니다.

좁히기를 유지하면 실제 변경을 놓칠 수 있고, 매번 해제하면 값을 바꾸지 않는 함수를 호출한 뒤에도 다시 확인해야 합니다.

앞의 장바구니 예제를 보면 알 수 있듯이 타입스크립트는 **함수 호출 뒤에도 좁히기를 유지하는 쪽**으로 동작합니다.
반복 확인의 부담을 줄이는 대신, `addItem`이 할인 정보를 비우는 변경은 놓친 셈입니다.

이렇게 좁혀진 타입과 실제 값이 달라질 수 있다면, 타입 검사를 통과했다는 이유만으로 안심하기는 어렵습니다. **함수 호출 전 확인한 값을 호출 뒤에도 그대로 써도 되는지** 살펴봐야 합니다.

우리 예제에서는 `addItem`이 비워둔 `cart.discount`에서 금액을 읽으려다 에러가 났습니다.

그렇다면 함수를 호출하기 전에 할인 객체를 별도의 변수에 담아두면 어떨까요?
장바구니의 할인 정보가 비워져도 기존 객체는 읽을 수 있을 겁니다.

<br/><br/>

## 지역 변수에 담아두면 어떨까요?

`const`로 지역 변수 `discount`를 선언해보겠습니다.

```tsx
function addItemAndShowDiscount(cart: Cart, newItem: Item) {
  const discount = cart.discount;
  //    ^? Discount | undefined

  if (discount) {
    addItem(cart, newItem); // cart.discount = undefined

    discount;
    // ^? Discount

    discount.amount; // 상품을 추가하기 전에 계산한 할인 금액
    //       ^? number
  }
}
```

`addItem`은 전달받은 장바구니 객체 `cart`를 직접 수정하므로, `cart.discount`는 `undefined`가 됩니다.
하지만 지역 변수 `discount`는 여전히 기존 할인 객체를 가리키므로, `discount.amount`를 읽어도 에러가 나지 않습니다.

함수 호출 후 읽는 할인 금액(discount.amount)은 상품을 추가하기 전의 낡은 값입니다.
**에러는 피했지만, 상품을 추가한 후의 장바구니 할인 금액으로 최신화하기 위해서는 다시 계산해야 합니다.**

앞에서는 런타임 에러로 문제가 드러났지만, 이번에는 잘못된 할인 금액이 화면에 표시될 수 있습니다.
**에러 없이 정상적으로 동작하니, 오히려 문제를 알아차리기 어려워졌습니다.**

<br/><br/>

## 바꾸지 않을 함수에는 readonly를 붙여봅시다

지금까지는 호출하는 쪽에서 값의 변경에 대처하는 방법을 살펴봤습니다.
이번에는 함수 안에서 의도하지 않은 변경을 줄이는 쪽으로 생각해보겠습니다.

장바구니를 읽기만 하는 함수라면, 인자를 `Readonly<Cart>`로 받아 속성에 직접 값을 할당하지 못하게 제한할 수 있습니다.

```tsx
function getTotalPrice(cart: Readonly<Cart>) {
  cart.discount = undefined;
  // TypeError: 읽기 전용 속성이므로 'discount'에 할당할 수 없습니다.
}
```

이번에는 호출부가 아니라 **함수 본문에서 타입 오류가 발생합니다.**

`Readonly<Cart>`로 받은 참조를 통해 `discount`에 직접 할당하는 것을 막아주는 겁니다.
함수에서 인자를 어떻게 다룰지 의도를 드러내고, 그 의도에 어긋나는 직접 할당을 잡아낼 수 있습니다.

다만 **`Readonly`를 붙였다고 함수가 객체를 바꾸지 않는다는 보장이 생기는 건 아닙니다.**

다음과 같은 한계점이 있죠.

<br/>

### readonly는 얕게 막습니다

```tsx
function inspectCart(cart: Readonly<Cart>, item: Item) {
  cart.items;
  //   ^? Item[]

  cart.discount = undefined; // 타입 오류
  cart.items.push(item); // 통과
}
```

`Readonly<T>`는 최상위 속성의 재할당을 막습니다.
`items`에 다른 배열을 넣지는 못해도, 그 배열에 상품을 추가할 수는 있습니다.

배열 변경까지 제한하려면 `readonly Item[]`을,
원소의 속성까지 제한하려면 그 안에도 읽기 전용 타입을 적용해야 합니다.

<br/>

### 다른 함수에 넘기면 값이 바뀔 수도 있습니다

직접 할당이 막힌다는 것은 확인했습니다.
그런데 같은 객체를 다른 함수에 넘기면 어떨까요?

```tsx
function addItem(cart: Cart, item: Item) {
  cart;
  // ^? Cart

  cart.items.push(item);
  cart.discount = undefined; // 여기서는 수정 가능
}

function inspectCart(cart: Readonly<Cart>, item: Item) {
  cart;
  // ^? Readonly<Cart>

  addItem(cart, item); // 타입 검사 통과
}
```

`inspectCart` 안에서는 `cart`가 읽기 전용인데, `addItem` 안에서는 수정할 수 있습니다.

**같은 객체인데, 각 함수가 그 객체를 다루는 타입이 다르기 때문입니다.**

`Readonly`는 객체 자체를 잠그는 기능이 아닙니다.
`Readonly<Cart>`라는 타입으로 다루는 곳에서 수정을 제한할 뿐입니다.

그렇다면 읽기 전용 객체를 수정 가능한 함수의 인자로 넘기는 것을 막아야 하지 않을까요?

하지만 타입스크립트는 일반 객체 타입끼리 호환되는지 검사할 때, 속성의 `readonly` 여부를 구분하지 않습니다. 그래서 이 예제에서는 `Readonly<Cart>`를 `Cart` 자리에 넘길 수 있습니다.

결국 `Readonly`는 **그 참조를 통한 직접적인 수정은 막지만, 다른 함수를 거친 수정까지 막아주지는 못합니다.**

따라서 `Readonly`를 붙였다는 이유만으로 “이 함수를 호출해도 값은 바뀌지 않는다”고 믿을 수는 없습니다.

<br/>

### 런타임에는 사라집니다

`readonly` 역시 타입 정보이므로 자바스크립트로 변환되면 사라집니다.
런타임에서도 수정을 막으려면 `Object.freeze` 같은 별도의 처리가 필요합니다.

다만 `Object.freeze`도 얕게 동작합니다. 중첩된 객체와 배열까지 막으려면 각각 동결해야 합니다.

<br/><br/>

## 정말 바꿔야 하는 함수는 어떻게 할까요?

`getTotalPrice`처럼 읽기만 하는 함수에는 `Readonly`를 붙이기 쉽습니다.
하지만 `addItem`은 장바구니를 바꾸는 함수입니다.

이 경우에는 인자를 직접 고치는 대신, 변경한 내용을 담은 새 객체를 돌려주는 방법이 있습니다.

```tsx
function withItem(cart: Readonly<Cart>, item: Item): Cart {
  return {
    ...cart,
    items: [...cart.items, item],
    discount: undefined, // 다시 계산이 필요한 상태
  };
}
```

(앞의 `addItem`과 구분하기 위해 이름을 `withItem`으로 바꿨습니다.)

이 구현은 원래 장바구니와 배열을 수정하지 않고, 상품을 추가한 새 장바구니를 돌려줍니다.
다만 기존 상품 객체까지 깊게 복사하는 것은 아닙니다.

<br/>

호출부는 이렇게 바뀝니다.

```tsx
let cart: Cart = {
  items: [{ name: '티셔츠', price: 30000 }],
  discount: { amount: 3000 },
};
const newItem: Item = { name: '바지', price: 50000 };

if (cart.discount) {
  cart.discount;
  //   ^? Discount

  cart = withItem(cart, newItem);

  cart.discount;
  //   ^? Discount | undefined
  // Cart 타입의 반환값으로 재할당하면서 좁히기가 풀립니다
}
```

이번에는 좁히기가 풀렸습니다.

`withItem`의 반환 타입은 `Cart`이고, 그 타입의 `discount`는 `undefined`일 수 있습니다.
새 값을 재할당했으니 이전에 확인한 조건을 그대로 적용할 수 없는 겁니다.

여기서 중요한 건 `Readonly` 자체보다 **변경을 새 값의 반환과 재할당으로 드러냈다는 점**입니다.
함수 안에서 몰래 바뀌던 상태가 호출부에도 보이게 된 셈입니다.

물론 이것만으로 할인 금액이 다시 계산되지는 않습니다.
현재 금액이 필요하다면 바뀐 상품 목록으로 할인 정보를 다시 계산해야 합니다.
다만 이제는 확인 없이 `cart.discount.amount`를 읽으면 타입 체커가 오류를 알려줍니다.

<br/><br/>

## 타입 검사를 통과했다는 것은

처음의 코드로 돌아가보겠습니다.

```tsx
if (cart.discount) {
  cart.discount;
  //   ^? Discount

  addItem(cart, newItem); // 런타임에는 cart.discount = undefined

  cart.discount;
  //   ^? Discount

  console.log(cart.discount.amount);
  //                        ^? number
  // 타입 검사 통과. 런타임에는 TypeError
}
```

`if`에서 확인할 때는 분명히 할인 정보가 있었습니다.

하지만 `addItem`을 호출하면서 `cart.discount`는 `undefined`가 됐습니다.

**타입 체커는 이 변경을 반영하지 않고, 호출 전에 좁혀둔 `Discount` 타입을 그대로 유지했습니다.**

그 결과, 실제로는 할인 정보가 사라졌는데도 `cart.discount.amount`에 접근하는 코드가 타입 검사를 통과했습니다.

이 사례는 타입 검사를 통과했다고 해서 런타임 안전성까지 보장되는 것이 아니라는 점을 보여줍니다.

<br/>

타입스크립트는 모든 런타임 동작을 빠짐없이 증명하는 타입 시스템을 목표로 하지 않습니다.
[공식 설계 목표 문서](https://github.com/microsoft/TypeScript/wiki/TypeScript-Design-Goals#non-goals)에도 다음 항목이 비목표(Non-goals)로 적혀 있죠.

> Apply a sound or "provably correct" type system.
> Instead, strike a balance between correctness and productivity.

건전하거나 증명 가능하게 올바른 타입 시스템을 적용하기보다는
정확성과 생산성 사이에서 균형을 잡겠다는 뜻입니다.

앞에서 본 타입 좁히기도 이런 선택을 보여줍니다.
함수 호출 뒤에도 좁혀둔 타입을 유지하면 값을 다시 확인하는 부담은 줄어들지만,
함수 안에서 일어난 변경을 놓칠 수 있습니다.

타입스크립트가 완벽한 안정성을 추구하며 모든 오류를 막기보다는
타입 안전성과 개발 편의성 사이의 균형을 택했음을 보여주는 사례입니다.

<br/>

타입 검사를 통과했다는 것은 런타임 안전성이 증명됐다는 의미가 아닙니다.
**타입스크립트가 검사하는 규칙과 가정 안에서 오류를 발견하지 못했다는 뜻**에 가깝습니다.

<br/>

지역 변수에 담아두면 기존 할인 객체를 읽을 수 있지만,
그 금액이 현재 장바구니에도 맞는지는 따로 확인해야 합니다.

`Readonly`는 직접적인 수정을 줄여주지만, 모든 변경을 막지는 못합니다.

새 객체를 반환하고 재할당하면 상태가 바뀌는 지점을 드러내어
타입 체커도 그 지점에서 좁히기를 다시 판단할 수 있었습니다.

<br/>

타입을 설계한다는 건 이런 차이를 알고, 의도하지 않은 변경이 일어날 자리를 줄여가는 일인 것 같습니다.
그러려면 **값이 언제, 어디서 바뀌는지 코드에 드러내는 것이 중요한 것 같습니다.**

이제는 좁혀진 타입만 보고 안심하기보다, 값을 확인한 시점과 사용하는 시점 사이에 어떤 일이 일어나는지 한 번 더 살펴보게 됐습니다. 타입 체커가 확인한 조건이 사용하는 순간에도 여전히 유효한지 보는 것이죠.

앞으로는 **변경이 일어나는 지점을 읽는 사람과 타입 체커 모두가 따라갈 수 있도록 코드를 작성하려고 합니다.**
