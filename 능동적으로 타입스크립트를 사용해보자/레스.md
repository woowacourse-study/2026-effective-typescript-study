# 능동적으로 타입스크립트를 사용해보자

저는 우아한테크코스 레벨2, 레벨3 동안 이펙티브 타입스크립트를 읽으면서 블로그에 글을 총 네 편정도 썼기때문에, 조금 종합적으로 나름 저만의 도메인 관점에서 바라보는, 즉 제품적인 관점으로 바라보는 타입스크립트에 대한 생각을 적고싶었습니다. 디자인 시스템 코드에서 설계 의도를 읽은 글, 쿠폰 도메인의 타입 설계를 돌아본 글, 유니온이 배타적이지 않은 이유를 다룬 글, optional never가 실제로 무엇을 막는지 확인한 글이였었는데요, 쓸 때는 매번 다른 주제라고 생각했는데... 다시 읽어 보니 모두 같은 고민에서 출발하고 있더라고요.

타입스크립트 문법을 많이 배울수록 같은 타입을 적는 방법도 여러가지를 알게 됩니다. 그러면 그중에 가장 짧은 표기를 고르면 되는 걸까요? 익숙한 방법으로 가면 될까요? 아니면 적기 전에 질문을 하나 먼저 던지고, 이 표기가 최선인지 계속 의심하면서 개발해야 하는 걸까요?

워밍업으로... Pick과 Omit부터 보겠습니다.

```ts
interface User {
  id: string;
  email: string;
  nickname: string;
  password: string;
}

type PublicUser = Omit<User, "password">;
type PickedPublicUser = Pick<User, "id" | "email" | "nickname">;
```

'아 4개중에 3개 쓰니까 Omit으로 1개만 빼서 바로 써야겠다!'

... 저 방금 코드를 치면서 어떤생각을 가지고 타입을 쳤죠? 방금 문장에 지금 도메인, 제품, 타입명에대한 관점에대한 생각이나 논리가 담긴 단어가 단 하나라도 있었나요?

비밀번호 하나만 빼면 되니까 Omit이 더 자연스러워 보입니다. Pick으로 쓰면 남길 필드 세 개를 다 나열해야 하고, 지금 만들어지는 타입은 둘이 똑같습니다. 솔직히 여기까지는 어느 쪽을 골라도 틀리지 않았어요.

그런데 반년 뒤에 `User`에 `passwordResetToken`이 추가되면 어떻게 될까요? Omit으로 만든 `PublicUser`에는 이 필드가 에러 없이 들어갑니다. Pick으로 만든 쪽에는 당연히 들어가지 않습니다. 우리는 잘 알고있지만 두 표기의 차이는 길이가 아니었습니다. 원본 타입에 필드가 늘었을 때 새 필드를 기본으로 내보내느냐, 기본으로 막아 두고 저에게 넣을지 말지를 묻느냐의 차이였습니다.

제 기존 타입스크립트 구현의 문제점이 보이셨나요? 사실 이 예시만 보면 반대로 생각하는 것도 괜찮긴 하죠. 예를들면, 

"아니죠. Public 이라는 타입명을 썼으면서 자연스럽게 Omit으로 Password를 뺀다음 타입명에 User를 붙이면 코드에서 바로 납득가고 나중에 읽을때에도 바로 이해가 가지 않겠어요?"

이런 상황을 하나 하나 고려하다보면 Pick 유틸리티를 쓰면서 동시에, Public 단어를 굳이 붙이지 말고(비밀번호를 빼버렸다는 이미지를 가져가는 타입명을 짓지말고), 정 반대의 측면에서 멀리서 한번 저 3가지의 필드를 나타내는 타입명을 천천히 고민해보면서 점점 코드의 품질을 개선시킬수도 있겠죠.

물론 정답은 없는 것 같습니다. 대신 서론에서는 트레이드 오프를 계속 고민하고 다음엔 어떻게 바뀔지, 그리고 내가 감당이 가능한지를 계속 고민하면서 타입을 설계해야한다는 의미를 강조하고 싶었어요. 그렇게 둘 유틸리티의 입장 차이를 알고 나니 타입을 적는 일이 다르게 보이게 되었고, 타입은 지금 값의 모양을 설명하기도 하지만, **다음 변경이 어디서 실패할지를 미리 정하는 일**이기도 합니다. 그리고 실패하는 자리에도 점점 스노우볼이 구르는 순서가 있었습니다.

그래서 어떤걸 선택할 것 같나구요? Omit으로 만든 `PublicUser`에는 반년 뒤에 필드가 추가되어도 에러 없이 조용하게 들어갈텐데, 제가 굳이 감당해야할까요?

## 스노우볼이 데굴데굴...

1. 값을 만드는 바로 그 줄에서 컴파일 에러가 납니다. 편집기에서 바로 보입니다.
2. 그 타입을 가져다 쓰는 다른 파일에서 컴파일 에러가 납니다. CI에서 보입니다.
3. 런타임 경계(서버 응답처럼 바깥 값이 앱으로 들어오는 지점)에서 걸리고, 지표에 남습니다.
4. 런타임 도중 예상하지 못한 곳에서 예외가 납니다. 사용자 화면에서 에러가 납니다.
5. 틀린 결과가 에러 없이 나갑니다. 아무도 모릅니다.

이 다섯 칸을 이 글에서는 간단하게 사다리라고 부르겠습니다. 1번이 맨 위이고, 위에서 걸릴수록 고치는 비용이 적습니다. 1번은 몇 초면 고치지만, 5번은 발견하는 데만 며칠이 걸리기도 합니다. 그래서 제가 생각하는 능동적인 설계는, 예상되는 변경마다 그 실패를 사다리에서 최대한 위로 끌어올리는 것입니다. 5번에서 드러날 실수를 1번에서 걸리게 만드는 것이죠. 다행입니다.

그러려고 타입을 적기 전에 던지게 된 질문이 3개정도 있습니다. 무엇을 적을지, 적을지 말지, 그리고 제대로 적어도 컴파일러가 확인하지 않는 부분을 무엇으로 막을지입니다. 뒤로 갈수록 타입만으로는 해결되지 않습니다. 제 프로젝트(버스 도착 예측 서비스, 연어 화이팅) 코드 대신에 도메인 설명 없이 읽을 수 있게 배송이나 결제처럼 누구나 아는 예로 진행해보겠습니다.

## 첫 번째 질문. 무엇을 적을까요?

### 아무 생각없이 받아쓴(받아 적던) 타입과, 계속계속 판단하며 적은 타입

주문의 배송 정보를 나타내는 타입부터 보겠습니다.

```ts
export type DeliveryStatus = "PREPARING" | "SHIPPED" | "DELIVERED";

export interface Delivery {
  status: DeliveryStatus;
  trackingNumber: string | null;
  shippedAt: string | null;
}
```

`status`가 무엇이든 `trackingNumber`(송장 번호)와 `shippedAt`(발송 시각)은 각자 null일 수 있습니다. 세 필드 사이에 아무 관계도 적혀 있지 않아서 이런 값도 전부 통과합니다.

```ts
{ status: "SHIPPED", trackingNumber: null, shippedAt: null }
{ status: "PREPARING", trackingNumber: "1234-5678", shippedAt: "2026-09-17T10:00:00+09:00" }
```

첫 번째 값은 발송했다면서 송장 번호가 없고, 두 번째 값은 아직 준비 중이라면서 송장 번호와 발송 시각이 있습니다. 도메인에서 두 필드가 비는 경우는 준비 중(`PREPARING`) 하나뿐인데, 타입은 이 관계를 모릅니다. 제가 적은 적이 없으니까요.

이 타입을 쓰는 코드에서도 문제가 드러납니다. 화면에서 `status`가 `SHIPPED`인지 확인한 다음 송장 번호를 보여 주려고 하면, `trackingNumber`가 여전히 `string | null`이라서 null 검사를 한 번 더 해야 합니다. 도메인에서는 일어날 수 없는 경우를 처리하는 분기가 코드에 남습니다.

```ts
export type Delivery =
  | { status: "PREPARING"; trackingNumber: null; shippedAt: null }
  | { status: "SHIPPED" | "DELIVERED"; trackingNumber: string; shippedAt: string };
```

발송을 했는지 안 했는지로 타입을 나눴습니다. 이렇게 공통 필드(`status`)의 값으로 멤버를 구분하는 유니온을 판별 유니온이라고 합니다. 이제 발송했다면서 송장 번호가 없는 값은 만드는 줄에서 컴파일 에러가 납니다. 그리고 `status`를 확인하면 그 분기 안에서 `trackingNumber`가 `string`으로 좁혀집니다. 조건문으로 확인한 뒤 분기 안에서 타입이 더 구체적으로 바뀌는 것을 좁히기라고 합니다. 책이 타입 설계 장을 시작하면서 내세우는 첫 원칙도 아래 문장과 같습니다.

> 효과적으로 타입을 설계하려면, 유효한 상태만 표현할 수 있는 타입을 만들어 내는 일이 가장 중요합니다. (p.182)

좀만 더 나아가서, 여기에 두 가지를 더 이야기하고 싶습니다.

첫째는 받아쓴 타입을 알아보는 방법입니다. 여기서 받아쓴 타입은 서버 응답 명세를 필드 순서 그대로 옮겨 적은 타입을 말합니다. 제 프로젝트에도 같은 파일 안에 상태별로 나눠 둔 타입과, 위처럼 필드를 나란히 둔 타입이 같이 있었어요. 둘 다 상태에 따라 있어야 하는 필드가 달라지는 구조인데 왜 한쪽만 나눴을까요? 나눠 둔 쪽은 처음부터 종류가 두 가지라고 생각하면서 직접 짰고, 나란히 둔 쪽은 서버 응답 명세를 그대로 옮겨 적었기 때문입니다. 그 명세는 필드 사이의 관계 없이 필드만 나열하고 있었고, 그걸 순서 그대로 옮기니 타입에서도 관계가 빠졌어요. 그래서 필드 순서가 명세와 같고 nullable 필드가 둘 이상 나란히 있는 타입은 받아쓴 타입일 가능성이 높습니다. 요즘은 이런 타입을 보면 필드 사이의 관계부터 확인해요.

둘째는 반대 방향의 실패입니다. 관계를 적는 도구에 익숙해지면 관계가 없는 곳에도 관계를 적게 됩니다. 예전에 쿠폰 타입을 설계하면서 최소 주문 금액 조건과 특정 상품 조건을 둘 중 하나만 가질 수 있게 묶었는데, 두 조건을 다 가진 쿠폰이 도메인에 실제로 있다는 걸 뒤늦게 알았어요. 있어야 할 관계를 안 적는 것과 없어야 할 관계를 적는 것은 반대처럼 보이지만 원인이 같습니다. 둘 다 타입을 적기 전에 도메인을 확인하지 않았습니다. 그래서 물어야 할 것은 "관계를 적었나요?"가 아니라 "받아쓴 타입인가요, 도메인을 보고 판단해서 적은 타입인가요?"입니다. 판단한 결과는 관계를 적는 쪽일 수도 있고 적지 않는 쪽일 수도 있습니다.

사다리로 보면, 관계 없이 받아쓴 타입에서는 불가능한 조합이 화면에 틀린 채로 나가거나(5번) 런타임에 null을 읽다가 예외가 납니다(4번). 관계를 적어 두면 값을 만드는 줄에서 막힙니다(1번).

### 원본과 파생 타입

처음에 본 Pick과 Omit으로 돌아가 보겠습니다. 원본 타입에서 만들어 낸 타입을 파생 타입이라고 하는데, 여섯 달 뒤를 그려 보면 파생 타입을 무엇으로 만드느냐가 길이 문제가 아닌 이유가 분명해집니다. 아래는 설명하려고 만든 가상의 타입입니다.

```ts
interface User {
  id: string;
  email: string;
  nickname: string;
  password: string;
  passwordResetToken: string; // 비밀번호 재설정 기능이 붙으면서 추가
  internalMemo: string; // 운영팀 메모, 추가
}

type PublicUser = Omit<User, "password">;
declare const omitted: PublicUser;
omitted.passwordResetToken; // 통과한다. 응답에 그대로 실린다

type PickedPublicUser = Pick<User, "id" | "email" | "nickname">;
declare const picked: PickedPublicUser;
picked.passwordResetToken;
// ~~~~~~~~~~~~~~~~~~ Property 'passwordResetToken' does not exist
```

`User`에 필드를 추가한 사람은 `PublicUser`가 있다는 걸 모를 수 있고, 안다고 해도 열어 보지 않습니다. 필드를 추가하는 작업만 했으니까요. 그런데 Omit으로 만든 `PublicUser`에는 두 필드가 자동으로 들어갑니다. 컴파일 에러도 없고, 응답 스냅샷 테스트를 안 짜 뒀다면 그대로 배포됩니다. Pick이었다면 새 필드는 들어오지 않습니다. 내보내고 싶으면 목록에 직접 적어야 하고, 그 순간 "아.. 이거 내보내도 되나?" 하고 한 번은 생각하게 됩니다.

`lib.es5.d.ts`를 열어 보면 둘의 관계가 보입니다.

```ts
type Pick<T, K extends keyof T> = { [P in K]: T[P] };
type Omit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>;
```

Omit은 Pick을 감싼 타입이고, 둘의 차이는 `K`에 걸린 제약 하나입니다. Pick의 `K`는 `T`의 키여야 하는데, Omit의 `K`는 아무 문자열이나 받습니다. 그래서 Omit은 오타도 못 잡습니다. `pageContents`를 빼려다가 `pageContent`라고 적으면 아무것도 안 빠진 채 원본과 똑같은 타입이 되는데, 컴파일러는 에러를 하나도 내지 않습니다.

그래서 Pick이 귀찮은 것은 단점이라기보다 기능입니다. Pick은 원본에 필드가 늘 때마다 넣을지 말지를 저에게 결정하게 하고, Omit은 그 결정을 대신 내려 주는데 기본값이 "포함"입니다. 허용 목록(allowlist)과 차단 목록(denylist)의 차이는 보안에서 오래된 이야기인데, 타입에도 똑같이 적용된다는 게 저한테는 새로웠어요.

그렇다고 Omit이 틀린 도구는 아닙니다. 원본에 필드가 늘 때 같이 따라가는 것이 의도라면 Omit이 맞습니다.

```ts
type MyButtonProps = Omit<ButtonProps, "onClick"> & { onPress: () => void };
```

`ButtonProps`에 `aria-label`이 추가되면 `MyButtonProps`도 따라가는 것이 맞습니다. 당근의 디자인 시스템인 SEED에서도 컴포넌트를 감싼 래퍼가 원본 props에서 `children`과 `asChild`만 빼고 전부 물려받습니다. 정리하면 API 응답처럼 밖으로 나가는 타입은 Pick, 원본을 물려받는 타입은 Omit입니다. 둘 중에 고를 때 물어야 할 것은 길이보다, 원본에 필드가 늘 때 이 타입도 같이 늘어나야 하는지입니다.

이 질문은 타입에서 끝나지 않고 데이터와 로직에서도 반복됩니다. 먼저 데이터입니다. 앞의 `ButtonProps`에 선택 속성 `size?: "large" | "medium"`이 있다고 하겠습니다. SEED 코드에서 본 패턴을 이 버튼에 옮기면, size마다 적용할 여백을 객체 하나에 표처럼 묶어 둘 수 있습니다.

```ts
const buttonPadding = {
  large: { x: 20, y: 12 },
  medium: { x: 16, y: 8 },
} as const satisfies Record<NonNullable<ButtonProps["size"]>, { x: number; y: number }>;
```

`satisfies`는 값의 타입을 바꾸지 않고, 그 값이 주어진 타입을 만족하는지만 검사합니다. `Record<K, V>`는 K에 속한 모든 키에 V가 있어야 하는 객체 타입이고, 여기서 키 목록은 `ButtonProps`의 `size`에서 가져옵니다. 그래서 size에 값이 하나 추가되면, 이 객체에 그 키를 채우기 전까지 컴파일 에러가 납니다.

다음은 로직입니다. 쿠폰 할인 여부를 판단하는 `assessCoupon` 함수는 쿠폰 종류(`discountType`)마다 case를 두는 switch문이고, default에서 `coupon`을 `never` 타입 변수에 할당합니다. `never`는 어떤 값도 들어갈 수 없는 타입이고, 이 방법을 흔히 `assertNever` 패턴이라고 부릅니다.

```ts
default: {
  const _exhaustive: never = coupon; // 새 discountType 추가 시 컴파일 에러
  return _exhaustive;
}
```

쿠폰 네 종류를 전부 처리했다면 default에 도달한 `coupon`의 타입은 `never`라서 통과합니다. 다섯 번째 종류가 추가되면 그 종류는 `never`에 할당할 수 없어서 바로 이 줄에서 에러가 납니다. 에러가 난 위치가 곧 "여기서 새 종류를 처리하지 않았다"는 안내가 됩니다.

셋은 도구가 다르지만 같은 질문에 답합니다. 원본이 바뀌었을 때, 원본에서 파생된 코드는 그걸 어디서 알게 되나요? Omit은 모르는 채로 에러 없이 따라갑니다. Pick은 파생 타입을 선언한 곳에서 사람이 직접 결정하게 합니다. `satisfies Record`와 `assertNever` 패턴은 파생 코드가 있는 파일에서 컴파일 에러로 알려 줍니다(2번). 원본을 고치는 사람이 파생 코드가 있는 줄 몰라도 컴파일러가 대신 찾아서 알려 주는 거죠. 결국 "누군가 기억하고 있겠지"에 기대지 않으려는 질문입니다.

## 두 번째 질문. 흠 적을까요, 말까요?

### 어기는 값이 없는 제약(뻘짓)

관계를 적는 도구에 익숙해지면 다음 문제는 필요 없는 곳에도 적는 것입니다. 제 프로젝트에서도 판별 유니온 여섯 개에 optional never를 넣었다가, 열아홉 줄 중 열여덟 줄을 다시 지운 적이 있어요.

optional never는 유니온의 다른 멤버에만 있는 키를 `?: never`로 선언해서, 그 키에 어떤 값이 들어와도 막는 방법입니다. 그런데 실제로 넣고 컴파일러로 확인해 보니 여섯 곳 중 다섯 곳에서는 아무것도 막고 있지 않더라고요. 값을 전부 객체 리터럴로 만들고 있어서, 초과 속성 검사(타입에 없는 속성을 적으면 에러를 내는 검사)가 이미 막고 있었기 때문입니다.

```ts
type Payment = { kind: "card"; cardNumber: string } | { kind: "cash" };

const literal: Payment = { kind: "cash", cardNumber: "1234" };
//                                       ~~~~~~~~~~ TS2353 초과 속성 검사가 잡는다

const wide = { kind: "cash" as const, cardNumber: "1234" };
const viaVariable: Payment = wide; // 통과한다. 변수를 거쳐 신선함을 잃어서 검사가 동작하지 않는다
```

초과 속성 검사는 객체 리터럴을 변수에 담지 않고 바로 대입할 때만 동작합니다. 타입스크립트는 이런 리터럴을 >>신선하다(fresh)<<라고 부릅니다. 변수에 한 번 담으면 신선함을 잃어서 검사가 동작하지 않고, 스프레드로 들어온 속성도 검사하지 않고, 서버에서 파싱한 값은 처음부터 신선하지 않습니다. optional never가 실제로 막는 값은 이렇게 초과 속성 검사가 동작하지 않는 경우에서만 나옵니다. 그래서 물어야 할 것은 멤버끼리 겹치지 않는다는 보장이 필요한지보다, 제 코드에서 값을 만드는 곳이 이 경우에 실제로 해당하는지입니다.

여섯 곳 중 해당하는 곳은 한 군데였어요. 공통 필드를 변수에 담아 두고, 멤버를 만들 때마다 스프레드로 펼치는 함수입니다.

```ts
export function toPaymentView(order: Order): PaymentView {
  const base = { orderId: order.id, amount: order.amount, paidAt: order.paidAt };

  if (order.paidWith === "cash") {
    return { kind: "cash", ...base };
  }
  // ...
}
```

해당하는 코드가 있으니 optional never를 남기는 것도 답이었습니다. 그런데 optional never가 필요한 이유가 스프레드 하나라면, 스프레드를 없애는 것도 답입니다. 멤버마다 키 세 개를 다시 적어야 하지만, 그 대신 반환값이 다시 신선한 리터럴이 되어서 초과 속성 검사가 다시 동작하고, optional never에 따라오던 비용도 사라집니다.

이 이야기의 핵심은 그 비용입니다. 아무것도 막지 않는 선언도 공짜가 아닙니다. optional never가 없으면 결제 수단을 좁히지 않고 `payment.cardNumber`를 읽는 순간 "현금 결제에는 이 속성이 없다"는 에러가 납니다. 그런데 현금 멤버에 `cardNumber?: never`를 선언하면 모든 멤버에 `cardNumber`가 생겨서, 좁히지 않고 읽어도 에러 없이 `undefined`가 나옵니다. 여기에 `??`로 기본값을 붙이면 현금 결제에도 그 기본값이 들어갑니다. 제 프로젝트에서도 실제로 이렇게 해서 라벨이 없어야 하는 항목에 라벨이 붙었는데, tsc도 eslint도 잡지 못했어요. `"cardNumber" in payment` 같은 `in` 검사도 모든 멤버에 `cardNumber`가 있으니 멤버를 가르지 못해서 좁히기가 멈춥니다. 선언을 더 엄격하게 하려고 넣은 한 줄이, 틀린 코드도 타입 검사를 통과할 수 있게 만들어버렸군요.

첫 번째 질문의 받아쓴 타입과 나란히 놓으면 둘이 정반대입니다. 받아쓴 타입은 적어야 할 것을 안 적은 실패이고, 여기서 본 optional never는 안 적어도 될 것을 적은 실패입니다. 둘 다 적기 전에 질문을 안 던져서 생겼습니다. 사다리로 보면, 어기는 코드가 없는 제약은 어떤 실패도 위로 올리지 못하면서 5번 실패가 생길 여지를 하나 더 만듭니다. 반면 어기는 코드가 있는 제약은 그 대입 줄에서 막습니다(1번).

### 도움을 받는 호출부

바로 앞에서 "막을 게 있나요?"를 고민해봤다면, 이번에는 "도움을 받는 코드가 있나요?"를 물어볼까요? 쿠폰 도메인을 설계할 때 모든 결정을 이 질문 하나로 걸렀어요. 이 타입을 추가하면 지금 당장 실제 호출부 하나라도 더 읽기 쉬워지거나 더 안전해지나요? 필드 하나짜리 인터페이스로 이 질문을 시험해 봤어요.

```ts
export interface MinimumOrderAmountRule {
  minimumOrderAmount: number;
}

export interface FixedCoupon extends CouponBase, MinimumOrderAmountRule {
  discountType: "fixed";
  discountAmount: number;
}
```

타입스크립트는 이름보다 모양(어떤 속성이 있는지)으로 타입을 비교합니다. 이를 구조적 타이핑이라고 합니다. 그래서 `extends MinimumOrderAmountRule`이라고 쓰든 `minimumOrderAmount: number`라고 직접 쓰든 만들어지는 타입은 같습니다. 컴파일러 입장에서는 아무것도 더해 주지 않는 인터페이스긴 하죠. 그런데 이 인터페이스를 필요로 하는 코드가 따로 있었어요.

```ts
type CouponWithMinimum = Extract<Coupon, MinimumOrderAmountRule>;
// => FixedCoupon | FreeShippingCoupon

function requiresMinimum(coupon: Coupon): coupon is CouponWithMinimum {
  return "minimumOrderAmount" in coupon;
}

export function assessCoupon(coupon: Coupon, ctx: OrderContext): boolean {
  if (isExpired(coupon, ctx.now)) return false;
  const orderAmount = calcOrderAmount(ctx.items);

  // 최소 주문 금액 게이트. 규칙을 가진 쿠폰은 전부 여기서 한 번에 거른다
  if (requiresMinimum(coupon) && orderAmount < coupon.minimumOrderAmount) return false;

  switch (coupon.discountType) {
    case "fixed":
      return true; // 게이트 통과로 충분
    // ...
  }
}
```

인터페이스가 있어야 타입 가드(`requiresMinimum`처럼 검사 결과로 타입을 좁혀 주는 함수)를 만들 수 있고, 타입 가드가 있어야 switch 앞에서 최소 주문 금액을 한 번에 거르는 조건문(코드 주석의 게이트)을 둘 수 있습니다. 그리고 이 조건문이 두 case에 똑같이 들어 있던 규칙을 한 곳으로 모읍니다. 인터페이스, 타입 가드, 조건문이 차례로 서로를 필요로 하고, 그 끝에 실제 코드 개선이 있는 구조입니다. 게다가 새 쿠폰 종류가 `MinimumOrderAmountRule`을 extends하는 순간, 최소 주문 금액이 없는 쿠폰 객체는 만들 수조차 없습니다.

```ts
const issued: FixedCoupon = { id: 1, code: "A", discountType: "fixed", discountAmount: 5000 };
//    ~~~~~~ Property 'minimumOrderAmount' is missing
```

5,000원 할인 쿠폰에 최소 주문 금액이 빠져서 3,000원짜리 양말에 쿠폰이 적용되고, 아무도 모르게 돈이 새는 실수를 떠올려 보겠습니다. 이런 실수를 리뷰어의 눈이나 쿠폰을 발행하는 사람의 기억에 맡기고 싶지 않아요. 타입 구조가 막아야 합니다. 인터페이스부터 조건문까지 이어진 이 연결 덕분에, 그 실수는 5번에서 쿠폰을 발행하는 줄(1번)로 올라옵니다.

반대로 검토했다가 넣지 않기로 한 도구들은 전부 그 도구를 필요로 하는 코드가 없었습니다.

| 넣지 않은 도구 | 넣지 않은 이유 |
| --- | --- |
| 금액 규칙을 모아 둔 `AmountRules`에서 Pick으로 골라 오기 | 골라낼 만큼 큰 원본 타입이 없음. 읽는 사람이 `AmountRules`를 한 번 더 찾아가야 하는 비용만 생김 |
| 쿠폰 종류별 표시 라벨을 담은 Record(라벨 맵) | 이 맵을 쓰는 코드가 없음. 빠진 종류 검사는 `assertNever` 패턴이 이미 해 줌 |
| 쿠폰 종류별 할인 계산 함수(핸들러)를 담은 Record(디스패치 테이블) | 정률 할인 핸들러가 정액 할인 핸들러의 결과를 입력으로 받아서, 핸들러 시그니처를 하나로 맞출 수 없음 |
| `discountType` 값으로 쿠폰 타입을 찾아 주는 `CouponByType<K>` | 이 제네릭을 쓰는 함수가 없음 |
| 중첩된 객체까지 readonly로 만드는 `DeepReadonly` | 라이브러리처럼 수백 곳에서 가져다 쓰는 코드에 맞는 도구. 도메인 코드에서는 읽기만 어려워짐 |

전부 매력적이고 손에 익은 도구였어요. 그래도 넣지 않은 이유는 하나입니다. 지금 코드에서 어떤 변경의 실패도 사다리 위로 올리지 못합니다. 넣은 것들은 서로를 필요로 해서 하나를 빼면 다른 것도 있을 이유가 사라지는데, 넣지 않은 것들은 필요로 하는 코드가 없어서 빼도 영향을 받는 코드가 없습니다.

리뷰어분과 나눈 대화도 사다리로 다시 정리할 수 있습니다. 리뷰어분은 `CouponBase` 아래에 최소 주문 금액을 가진 중간 타입을 두는 방식, 그러니까 쿠폰 유형을 계층으로 나누는 방식을 떠올리셨고, 저는 최소 주문 금액 같은 정책을 인터페이스로 떼어 냈어요. 두 방식 모두 쿠폰을 발행하는 줄에서 막습니다(1번). 차이는 정책이 둘 이상 조합될 때 드러납니다. 유형 계층은 조합마다 중간 타입을 새로 만들어야 하고, 하나라도 빠뜨리면 그 조합의 쿠폰은 발행하는 줄에서 막히지 않아 더 아래 번호로 내려갑니다. 정책 하나만 담은 인터페이스는 `extends A, B, C`처럼 나열하면 조합이 끝납니다. 그리고 첫 번째 질문에서 말한 것처럼 두 조건을 다 가진 쿠폰은 이미 도메인에 있습니다. 그래서 이 비교는 먼 미래를 가정하지 않아도 지금 도메인만 보고 판단할 수 있습니다.

## 세 번째 질문. 컴파일러가 확인하지 않는 부분은 무엇으로 막을까요?

타입스크립트의 설계 목표 문서(Design Goals)에는 하지 않기로 한 것들의 목록인 Non-goals가 있습니다. 그중 3번은 무결한(sound) 타입 시스템, 그러니까 타입 검사를 통과하면 런타임 타입 에러가 절대 없다고 보장하는 타입 시스템을 만들지 않고 정확성과 생산성 사이에서 균형을 잡겠다는 내용입니다. 5번은 런타임 타입 정보를 만들지도, 거기에 기대지도 않겠다는 내용입니다. 책도 같은 이야기를 합니다.

> 사실 타입스크립트는 무결성을 달성하기 위해 만들어진 것이 아닙니다. 무결성 대신, 사용의 편의성과 함께 이미 존재하는 자바스크립트와의 호환성을 우선시합니다. (p.271)

그러니 타입 검사를 통과했다는 것은 안전하다는 뜻이 아니라, 제가 적은 규칙끼리 서로 모순이 없다는 뜻입니다. 규칙이 도메인과 맞는지는 앞의 두 질문이 맡았습니다. 여기서는 제대로 적어도 컴파일러가 확인하지 않는 세 가지를 보겠습니다. 값을 바꾸는 주체, 런타임에 들어오는 값, 시간이 지나며 느슨해지는 규칙입니다.

### 값을 바꾸는 주체

리액트로 컴포넌트를 짜다가 이런 코드를 만난 적이 있어요.

```tsx
interface User {
  name?: string;
}

function Profile({ user }: { user: User }) {
  if (!user.name) return null;

  return <button onClick={() => alert(user.name.toUpperCase())} />;
  //                                  ~~~~~~~~~ 'user.name' is possibly 'undefined'
}
```

오! 맨 위에서 이미 걸렀습니다. `name`이 없으면 `null`을 반환하고 끝나는데, `onClick` 안에서는 또 `undefined`일 수 있다고 합니다. 그때는 리액트 문제인 줄 알았어요. 구조 분해로 바꾸니 에러가 사라져서 그냥 넘어갔는데... 아이템 23을 읽고 나서야 우연이 아니었다는 걸 알았어요. 리액트를 전부 걷어내도 똑같이 재현됩니다.

```ts
function greetLater(user: User) {
  if (!user.name) return;

  setTimeout(() => {
    user.name.toUpperCase(); // 'user.name' is possibly 'undefined'
  });
}

function greetLaterLocal(user: User) {
  const name = user.name;
  if (!name) return;

  setTimeout(() => {
    name.toUpperCase(); // 정상
  });
}
```

타입 좁히기는 값 자체보다 `user.name` 같은 이름(참조)에 붙습니다. 그리고 그 이름이 객체 속성이면 좁혀진 타입은 그 코드 위치에서만 유효합니다. `setTimeout`에 넘긴 함수는 언제 실행될지 모르고, 그 사이에 누가 `user.name`을 지웠는지 알 방법이 없으니 타입스크립트는 좁히기를 포기합니다. 반면 `const name`은 이 함수 안에서만 쓰여서 재할당되는지를 컴파일러가 전부 확인할 수 있고, 그래서 콜백 안에서도 좁혀진 타입이 유지됩니다.

그런데 정반대인 경우도 있습니다. 콜백에서는 이렇게 깐깐하게 확인하면서, 함수 호출은 그냥 넘어갑니다.

```ts
function clear(user: User) {
  delete user.name;
}

function greet(user: User) {
  if (user.name) {
    clear(user);
    user.name.toUpperCase(); // 타입 오류 없음. 런타임에서 TypeError
  }
}
```

`clear`가 `name`을 지우는데 타입스크립트는 아무 에러도 내지 않고, 실행하면 당연히 TypeError가 납니다. 타입스크립트가 이 동작을 몰라서 그런 것이 아닙니다. 원칙대로라면 함수를 호출할 때마다 좁혀 둔 타입을 원래대로 되돌려야 맞는데, 그러면 호출할 때마다 검사를 다시 써야 해서 아무도 그렇게 코드를 못 씁니다. 그래서 타입스크립트는 함수를 호출해도 좁혀 둔 타입(책의 표현으로는 타입 정제)이 그대로라고 가정합니다(p.152). 대부분의 함수는 인자를 바꾸지 않는다는 쪽에 건 것이고, 인자를 바꾸는 소수의 함수는 컴파일러가 확인하지 않습니다. 앞에서 본 Non-goals 3번처럼 정확성보다 생산성을 택한 결정입니다.

두 현상은 반대처럼 보이지만 같은 질문으로 모입니다. 이 값을 누가 바꿀 수 있나요? 컴파일러는 그 답을 모르니까 콜백에서는 누군가 바꿨을 거라고 가정하고, 함수 호출에서는 아무도 안 바꿨을 거라고 가정합니다. 능동적인 설계는 그 답을 제가 정해서 함수 시그니처에 적어 두는 일입니다. 함수가 인자를 바꾸지 않는다면 `readonly`로 받습니다.

```ts
function clearReadonly(user: Readonly<User>) {
  delete user.name; // The operand of a 'delete' operator cannot be a read-only property
}

function findMedian(scores: readonly number[]) {
  scores.sort(); // Property 'sort' does not exist on type 'readonly number[]'
  // 비교 함수를 넘겨도 원본 배열이 바뀌는 건 같다
}
```

호출하는 쪽은 `readonly`가 아닌 배열도 그대로 넘길 수 있어서 추가 비용이 없습니다. 중앙값을 구하려고 무심코 `sort`를 부르면 넘겨받은 배열의 순서까지 바뀌는데, `readonly`로 받으면 그 줄에서 막힙니다. 컴파일러가 확인하지 않기로 한 "함수 호출 뒤"를 "함수 안"에서 대신 확인하고있네요. 다만 `readonly`는 한 단계만 막아서, 객체 안에 있는 객체의 속성까지 막지는 않습니다. 책도 직접 작성한 함수가 매개변수를 변경하지 않는다면 `readonly`로 선언하라고 합니다. 변경하면서 생기는 에러를 막을 뿐 아니라, 변경이 일어나는 코드를 찾기도 쉬워지기 때문입니다(p.94~95).

제 프로젝트에서도 불일치를 하나 발견했어요. 입력 배열을 바꾸지 않는 계산 함수가 두 개 있었는데, 하나는 배열을 `readonly`로 받고 다른 하나는 그냥 `number[]`로 받고 있었어요. 지금 당장 문제는 없습니다. 하지만 책에 나오듯 `readonly`는 그 배열을 넘겨받는 다른 함수들로 퍼져 나가는 경향이 있고(p.94), 반대로 `readonly`가 없는 곳은 나중에 `sort` 한 줄이 들어와도 아무도 모릅니다. 같은 프로젝트에서 같은 성격의 함수가 서로 다르게 선언돼 있으면, 그것은 설계했다기보다 그날 기분에 따라 적은 것입니다.

콜백 안에서 쓸 값은 지역 변수로 꺼내 둡니다. 대가는 있습니다. 지역 변수는 그 순간의 값을 복사한 것이라서 원본이 바뀌어도 따라 바뀌지 않습니다. 타입은 믿을 수 있게 된 대신 값이 오래된 것일 수 있습니다. 책은 그래도 지역 변수 쪽이 낫다고 하고, 저도 그렇게 생각합니다. 값을 복사해 뒀다는 건 코드에 드러나서 오래된 값일 수 있다는 걸 알 수 있지만, 타입이 틀렸다는 건 코드만 봐서는 알 수 없기 때문입니다.

한 단계 더 거슬러 올라가면, 이 문제는 `name?: string`이라는 선택적 속성에서 시작합니다. 선택적 속성이 없으면 좁힐 일도, 좁혀 둔 타입이 풀릴 일도 없습니다. 책 아이템 37의 예가 이 글의 주장을 그대로 보여 줍니다. 기존 코드에 영향을 주지 않으려고 단위 시스템 옵션을 `unitSystem?`로 추가했더니, 이 옵션을 넘기지 않은 호출부가 생겨서 미터법 사용자가 영국식 단위를 보게 됩니다. 필수 속성으로 바꾸면 `unitSystem`을 넘겨야 하는 모든 곳에 에러가 표시되는데, 책은 이렇게 적습니다.

> 표시된 모든 오류를 하나씩 수정해야 하지만, 사용자로부터 불평을 듣는 것보다는 나은 선택입니다. (p.220)

사다리로 옮기면 딱 맞는 문장입니다. 속성을 선택적으로 만드는 것은, 실패가 드러나는 곳을 1번(컴파일 에러)에서 5번(틀린 화면이 에러 없이 나가는 경우)으로 내리는 결정입니다. 같은 식으로 보면, 누가 값을 바꿀 수 있는지 묻지 않을 때 함수 호출 뒤의 변경은 런타임 예외(4번)가 되고, 콜백의 possibly undefined 에러는 습관처럼 붙인 `?.`에 가려져서 에러 없는 틀린 결과(5번)가 됩니다. `readonly`는 값을 바꾸려는 코드를 그 줄에서 막고(1번), 지역 변수는 콜백 안에서도 좁혀 둔 타입을 지킵니다.

### 런타임에 들어오는 값

아래는 서버 응답을 해석하는 함수입니다. JSON 자체가 깨진 응답은 이 함수를 부르기 전에 `malformed`로 처리합니다.

```ts
function interpret<T>(response: Response, body: unknown): ApiResult<T> {
  if (response.ok) {
    return { ok: true, data: body as T };
  }

  if (isErrorResponse(body)) {
    return { ok: false, kind: "server-error", error: body };
  }

  return { ok: false, kind: "malformed" };
}
```

응답 본문을 `unknown`으로 받은 것까지는 솔직히 괜찮습니다. 그런데 결국 `body as T`로 단언합니다. 타입 단언(`as`)은 컴파일러에게 "이 값은 이 타입"이라고 알려 주는 문법이라 검사 없이 통과합니다. 이 한 줄 뒤로는 앱 전체가 응답이 `T` 타입이라고 믿고 동작합니다. 서버가 필드 하나를 빼먹거나 숫자를 문자열로 바꿔 보내도 컴파일러는 아무 에러도 내지 않습니다. 낼 수가 없습니다. 타입은 컴파일이 끝나면 지워지니까요. 그러니 제가 공들여 짠 타입 파일은 서버 응답이 이렇게 올 거라는 명세를 적어 둔 문서일 뿐이고, 응답이 실제로 명세를 지키는지 확인하는 장치는 아닙니다.

같은 함수 안에서 실패 응답과 성공 응답을 다르게 다루고 있습니다. 실패 응답은 `isErrorResponse`라는 타입 가드로 런타임에 검사하는데, 성공 응답은 단언만 합니다. 실패 응답은 클라이언트가 실패 종류를 직접 정해야 해서 검사가 필요했고, 성공 응답은 그대로 앱에 넘기면 되니까 검사할 이유가 없었던 것입니다. 검증 코드는 위험한 곳보다 필요가 생긴 곳에 먼저 생긴 거죠. 그런데 앱에 넘기는 성공 응답이야말로 앱 전체로 가장 넓게 퍼지는 값인데, 그 값이 앱으로 들어오는 지점에는 검사가 없었습니다.

여기에 넣을 것은 런타임 스키마입니다. 책은 타입 정보와 검증 로직을 따로 관리하는 것을 최악의 중복이라고 부르고(p.426), 둘을 한 곳에서 정의하는 방법으로 zod(런타임에 값의 모양을 검사하는 라이브러리)를 소개합니다.

(zod에 관심 없다면 넘어가셔도 좋습니다)

```ts
const DeliverySchema = z.discriminatedUnion("status", [
  z.object({ status: z.literal("PREPARING"), trackingNumber: z.null(), shippedAt: z.null() }),
  z.object({
    status: z.enum(["SHIPPED", "DELIVERED"]),
    trackingNumber: z.string(),
    shippedAt: z.string(),
  }),
]);

export type Delivery = z.infer<typeof DeliverySchema>;
```

첫 번째 질문에서 적은 판별 유니온과 같은 모양인데, 이제는 타입이 스키마에서 만들어집니다. 명세를 적는 문서와 명세를 확인하는 장치가 같은 코드에서 나오니까 둘이 어긋날 수가 없습니다. 클라이언트에서 바꿀 부분도 크지 않습니다. 단언하던 자리에서 스키마로 검사하고, 검사에 실패하면 새 실패 종류로 돌려주면 됩니다.

```ts
function interpret<T>(response: Response, body: unknown, schema: z.ZodType<T>): ApiResult<T> {
  if (response.ok) {
    const parsed = schema.safeParse(body);
    if (!parsed.success) {
      return { ok: false, kind: "schema-mismatch", issues: parsed.error.issues };
    }
    return { ok: true, data: parsed.data };
  }
  // 실패 응답 처리는 위와 같다
}
```

스키마는 요청하는 쪽이 엔드포인트마다 넘깁니다. 그래서 이 함수는 응답이 어떤 모양이어야 하는지 몰라도 되고, 모양은 스키마를 가진 쪽이 책임집니다. 이 앱은 요청이 실패하면 60초 뒤에 다시 요청하고, 화면에는 마지막으로 성공한 응답을 계속 보여 줍니다. 재시도와 화면 처리에서 `schema-mismatch`를 `malformed`와 똑같이 다루면, 명세와 다른 응답을 화면까지 보내는 대신 검증을 통과한 직전 값을 보여 주면서 다음 응답을 기다리게 됩니다. 그러면서도 `kind`가 다르니까 지표에서는 JSON이 깨진 경우와 명세와 다른 경우를 따로 셀 수 있고, `issues`에는 어떤 필드가 왜 어긋났는지가 남습니다. 서버 로그와 맞춰 보려면 응답의 요청 ID도 같이 남겨야 합니다. 검증도 실행 중에 아무도 모르게 실패하면 타입이 없는 것과 같습니다. 검증이 실패했다는 사실이 지표에 남아야 검증을 넣은 의미가 생깁니다.

### 시간이 지나며 느슨해지는 규칙

이것은 코딩 에이전트와 같이 일하게 되면서 새로 생긴 문제입니다. 요즘은 코드를 혼자 다 쓰지 않잖아요. 에이전트가 타입 에러를 만나면 방법이 두 가지입니다. 코드를 고치거나, 타입을 고치거나요. 그리고 타입을 고치는 쪽이 거의 항상 더 짧습니다. `as`를 붙이거나, `!`를 붙이거나, 필드에 `?`를 붙이거나, `| null`을 더하는 식입니다. 전부 다섯 글자 이내이고 전부 컴파일을 통과합니다. 사람도 급하면 그렇게 하는데, 에이전트는 급한 게 기본값입니다.

이 문제에 대비해 이미 만들어 둔 게 하나 있어요.

```ts
// delivery.typeTest.ts

function rejectsTrackingNumberWhilePreparing(): Delivery {
  const smuggled = { status: "PREPARING" as const, trackingNumber: "1234", shippedAt: null };
  // @ts-expect-error 준비 중(PREPARING)인데 송장 번호를 채우면 막혀야 한다
  const delivery: Delivery = smuggled;
  return delivery;
}

// 아래는 정상 코드다. status로 분기하면 trackingNumber가 string으로 좁혀지는지 확인한다.
function narrowsTrackingNumberByStatus(delivery: Delivery): string {
  if (delivery.status !== "PREPARING") {
    return delivery.trackingNumber;
  }
  return "";
}
```

일부러 틀린 코드를 써 두고 `@ts-expect-error`로 에러를 덮어 둡니다. 누군가 준비 중 멤버의 `trackingNumber`를 `string | null`로 느슨하게 고쳐서 에러가 사라지면, 이번에는 `@ts-expect-error` 쪽이 "기대한 에러가 없다"는 에러를 냅니다. CI에서 `tsc --noEmit`을 돌리니까 거기서 걸립니다. 책은 이것을 부정적 테스트라고 부릅니다(p.326). 앞에서 타입 검사는 규칙끼리 모순이 없는지만 확인한다고 했는데, 이 테스트는 규칙을 느슨하게 만드는 변경을 규칙끼리의 모순으로 바꿔서 컴파일러가 잡게 만듭니다. 정상 코드를 짝으로 두는 이유는 `@ts-expect-error`가 어떤 에러가 났는지는 따지지 않기 때문입니다. 부정 테스트는 막혀야 할 코드가 막히는지를, 긍정 테스트는 통과해야 할 코드가 통과하는지를 확인합니다.

그리고 타입 검사를 우회하는 방법 중 무엇이 프로젝트에서 아직 막혀 있지 않은지 세어 봤어요.

| 우회 방법 | 지금 상태 | 막는 규칙이나 파일 |
| --- | --- | --- |
| `any` | 막힘 | `no-explicit-any` (typescript-eslint recommended) |
| `@ts-ignore` | 막힘 | `ban-ts-comment` |
| `@ts-expect-error` | 설명을 달아야 통과 | `ban-ts-comment`의 allow-with-description |
| `as T` | 안 막힘 | 없음. 클라이언트에 두 곳 있음 |
| `!` | 안 막힘 | 없음 |
| 필드에 `?`나 `\| null` 추가 | 특정 필드만 막힘 | 타입 테스트 파일 |

위의 세 가지는 recommended 설정만으로 이미 막혀 있었습니다. 막혀 있지 않은 것은 단언 두 가지(`as`, `!`)와 타입 자체를 느슨하게 고치는 방법입니다. 단언을 막을 때는 순서가 있습니다. 런타임 검증을 넣으면 클라이언트의 `body as T`가 사라지고, 남는 `as`는 `isErrorResponse` 타입 가드 안의 하나뿐입니다. 그것까지 스키마로 바꾸면 프로젝트에서 `as` 단언이 0개가 되고, 그때 `consistent-type-assertions`의 `assertionStyle`을 `never`로 두면 `as` 단언을 린트로 금지할 수 있습니다. `as const`는 이 규칙이 예외로 허용합니다. `!`는 이 규칙이 막지 않아서 `no-non-null-assertion` 규칙을 따로 켜야 하고, 코드에 남은 `!`를 먼저 null 검사로 바꾼 다음에 켭니다. 대신할 코드 없이 금지부터 하면 컴파일되지 않는 코드가 생기고, 결국 누군가 규칙에 예외를 추가하게 됩니다. 그래서 금지 규칙은 런타임 검증이나 null 검사처럼 단언을 대신할 코드를 먼저 넣은 다음에 켜야 합니다.

사다리 번호로 정리하면, 타입 테스트는 타입을 느슨하게 만드는 변경을 CI의 컴파일 에러(2번)로 올립니다. 런타임 검증은 서버 명세가 바뀐 걸 런타임 경계(3번)에서 잡습니다. 그리고 검증 실패를 지표로 기록하지 않으면, 경계에서 잡았다고 해도 아무도 모른 채 사라집니다(5번).

---

세 질문을 표 하나로 모으면 다음과 같습니다.

| 질문 | 안 던지면 실패가 드러나는 곳 | 던지면 실패가 드러나는 곳 | 도구 |
| --- | --- | --- | --- |
| 무엇을 적을까 | 런타임 예외(4), 에러 없는 틀린 결과(5) | 값을 만드는 줄(1), 파생 코드가 있는 파일(2) | 판별 유니온, Pick, `satisfies Record`, `assertNever` 패턴 |
| 적을까, 말까 | 위로 올린 실패 없이 비용만 생김 | 대입하는 줄(1), 쿠폰을 발행하는 줄(1) | 값을 만드는 코드 수정, 그 타입을 필요로 하는 코드가 있는지 확인 |
| 컴파일러가 확인하지 않는 부분은 무엇으로 막을까 | 런타임 예외(4), 에러 없는 틀린 결과(5) | 값을 바꾸는 줄(1), CI(2), 런타임 경계(3) | `readonly`, 지역 변수, 타입 테스트, 런타임 스키마, 검증 실패 기록 |

돌아보면 타입을 붙이는 사람과 설계하는 사람의 차이는 아는 문법의 개수가 아니었던 것 같네요. 세 질문 모두 새로운 문법이 필요하지 않습니다. 차이는 타입을 적기 전에 다음 변경을 그려 보는지, 그리고 그 변경이 어디서 실패할지를 고르는지에 있었습니다. 예전에 현실에서 가능한 상태는 그대로 담고 불가능한 상태만 담을 수 없게 만드는 걸 제 타입 설계 목표로 적은 적이 있는데, 세 질문을 지나고 나니 한 줄이 더 붙습니다. **타입 설계는 다음 변경이 어디서 실패할지 고르는 일이고, 좋은 설계는 그 실패를 사다리에서 가장 고치기 싼 곳까지 끌어올립니다. 끌어올릴 수 없는 실패는 지표로 기록해서 지켜봅니다.**
