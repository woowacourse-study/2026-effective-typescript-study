# 타입 중복을 줄이는 게 항상 정답일까?

만약 백엔드에서 API 응답 필드 하나를 변경했는데 프론트엔드의 타입을 수정하지 않는다면 어떻게 될까?

```diff
{
  status: "success",
  data: {
    id: 1,
-    title: "shout-outz",
+    name: "shout-outz",
  }
}
```

```ts
interface ProjectResponse {
  id: number;
  title: string;
}
```

최근 팀 프로젝트를 시작하고 컨벤션을 정하는 과정에서 이런 불일치를 어떻게 줄일 수 있을지 고민했다.

그러던 중 백엔드의 API 명세를 바탕으로 프론트엔드에서 사용할 API 타입을 생성하면 이런 문제를 최소화할 수 있겠다는 생각이 들었다.

찾아보니 실제로 이를 위한 도구들도 존재했고, 모노레포 구조인 우리 프로젝트에 적용하기에도 적합해 보였다.

본격적으로 적용하기에 앞서 한 가지 고민이 생겼다.

생성된 API 타입을 프론트엔드에서는 어디까지 기준으로 사용해야 할까?

API 응답과 프론트엔드에서 데이터를 사용하는 형태가 같다면 생성된 타입을 그대로 사용할 수 있다.

그렇지 않더라도 생성된 API 타입을 기준으로 `Pick`, `Omit` 같은 타입 연산을 이용해 프론트엔드에서 필요한 타입을 파생하면 되지 않을까 생각했다.

## 생성된 API 타입에서 프론트엔드 타입까지 파생하기

예를 들어 프로젝트 API의 응답이 다음과 같다고 해보자.

```ts
// generated

interface ProjectResponse {
  id: number;
  name: string;
  description: string;
  thumbnailUrl: string;
  likeCount: number;
  categories: CategoryResponse[];
}
```

프론트엔드에서 프로젝트 카드를 표현하기 위해 이 중 일부만 사용한다면 `Pick`을 이용할 수 있다.

```ts
type ProjectCard = Pick<ProjectResponse, 'id' | 'name' | 'thumbnailUrl' | 'likeCount'>;
```

수정 폼에서 일부 값만 다룬다면 `Partial`과 `Pick`을 조합할 수도 있다.

```ts
type ProjectEditForm = Partial<Pick<ProjectResponse, 'name' | 'description' | 'thumbnailUrl'>>;
```

이렇게 하면 `name`, `description`, `thumbnailUrl` 같은 타입 정보를 반복해서 작성하지 않아도 된다.

`ProjectResponse`의 `thumbnailUrl` 타입이 변경된다면 이를 파생한 타입에도 자연스럽게 반영된다.

이펙티브 타입스크립트의 **아이템 15 「타입 연산과 제네릭 사용으로 반복 줄이기」**에서도 `Pick`, `Partial`, `typeof` 같은 타입 연산을 이용해 이미 존재하는 타입 정보를 반복하지 않는 방법을 소개한다.

여기까지만 생각하면 생성된 API 타입을 SSOT로 두고 프론트엔드에서 사용하는 타입도 최대한 여기에서 파생하는 것이 자연스러워 보였다.

## 그런데 모든 도메인 타입을 특정 API 타입에서 파생할 수 있을까?

조금 더 생각해보니 관계가 그렇게 단순하지만은 않았다.

같은 `Project`를 다루더라도 API의 목적에 따라 표현되는 형태가 달라질 수 있다.

예를 들어 프로젝트 목록에서는 목록을 그리는 데 필요한 정보만 내려줄 수 있다.

```ts
interface ProjectListItemResponse {
  id: number;
  name: string;
  thumbnailUrl: string;
  likeCount: number;
}
```

반면 프로젝트 상세 API에서는 다른 정보가 필요할 수 있다.

```ts
interface ProjectDetailResponse {
  id: number;
  name: string;
  description: string;
  categories: CategoryResponse[];
  likeCount: number;
}
```

프론트엔드 내부에서는 두 API와는 또 다른 형태로 `Project`를 다룰 수도 있다.

```ts
interface Project {
  id: number;
  name: string;
  description: string;
  thumbnailUrl: string;
  categories: Category[];
}
```

그렇다면 이 `Project`는 어느 API 타입에서 파생해야 할까?

프로젝트 생성 API까지 고려하면 표현은 더 다양해진다.

```ts
interface CreateProjectRequest {
  name: string;
  description: string;
  categoryIds: number[];
}

interface CreateProjectResponse {
  id: number;
  name: string;
  description: string;
  categories: CategoryResponse[];
}
```

같은 `Project`를 다루지만 생성 요청에서는 `categoryIds`를 보내고 응답에서는 `CategoryResponse` 객체를 받는다.

즉 같은 도메인을 다루더라도 목록 응답, 상세 응답, 생성 요청, 생성 응답, 프론트엔드 내부 모델은 각각의 목적에 따라 다른 형태를 가질 수 있다.

물론 이런 차이도 타입 연산을 조합해 표현할 수 있다.

하지만 서비스가 고도화되고 API와 요구사항이 늘어나면 그 관계 역시 점점 복잡해질 수 있다.

## 타입을 파생하는 관계 자체도 의존성이다

앞의 `Project`를 API 타입에서 최대한 파생한다면 다음과 같이 표현할 수도 있다.

```ts
type Project = Pick<ProjectDetailResponse, 'id' | 'name' | 'description'> &
  Pick<ProjectListItemResponse, 'thumbnailUrl'> & {
    categories: Category[];
  };
```

타입 시스템에서는 문제없이 표현할 수 있고 중복도 줄어든다.

하지만 이제 `Project`라는 타입을 이해하려면 `ProjectDetailResponse`와 `ProjectListItemResponse`를 함께 확인해야 한다.

API가 늘어나고 더 많은 타입을 조합하기 시작하면 이런 관계도 계속 늘어난다.

처음에는 타입의 중복을 줄이기 위해 만든 파생 관계지만, 동시에 프론트엔드의 `Project`가 여러 API 타입에 의존하는 구조를 만든 셈이다.

타입을 파생한다는 것은 단순히 같은 타입 선언을 반복하지 않는 것만을 의미하지 않는다.

```ts
type ProjectCard = Pick<ProjectResponse, 'id' | 'name'>;
```

이렇게 선언하면 `ProjectCard`의 `id`와 `name`은 앞으로 `ProjectResponse`의 변경을 따라간다는 관계까지 함께 표현하게 된다.

그 관계가 실제로 필요한 관계라면 문제가 없다. 오히려 타입 연산을 사용해야 하는 이유가 된다.

반대로 서로 독립적으로 변경될 수 있는 타입이라면 중복을 없애기 위해 만든 파생 관계가 불필요한 의존성이 될 수도 있다.

## 모든 중복을 없애야 하는 것은 아니다

이펙티브 타입스크립트에서도 무조건적으로 타입의 중복을 줄여야 한다고 이야기하지 않는다.

아이템 15에서는 타입 연산과 제네릭을 이용해 반복을 줄이는 방법을 설명하면서도 이를 지나치게 적용하는 것을 경계한다.

서로 독립적으로 변화할 수 있는 타입을 하나의 추상화로 묶으면 오히려 각각의 타입이 독립적으로 변화하기 어려워질 수 있다는 것이다.

API 타입과 프론트엔드 도메인 타입의 관계도 비슷하게 볼 수 있다.

API 타입은 서버와 프론트엔드가 **어떤 형태의 데이터를 주고받을지**를 표현한다.

```ts
interface ProjectResponse {
  id: number;
  name: string;
  description: string;
}
```

프론트엔드 도메인 타입은 같은 `Project`를 애플리케이션 내부에서 **어떤 형태로 다루고 사용할지**를 표현한다.

```ts
interface Project {
  id: number;
  name: string;
  description: string;
}
```

현재는 두 타입의 형태가 같다.

하지만 변경되는 이유까지 같은 것은 아니다.

예를 들어 백엔드의 API 설계가 변경되면서 응답 필드의 이름이 바뀔 수 있다.

```ts
interface ProjectResponse {
  id: number;
  projectName: string;
  description: string;
}
```

그렇다고 프론트엔드 내부에서 사용하던 `Project.name`까지 반드시 `projectName`으로 변경해야 하는 것은 아니다.

```ts
interface Project {
  id: number;
  name: string;
  description: string;
}
```

반대로 프론트엔드에서 데이터를 사용하는 방식이 달라져 `Project` 타입이 변경되더라도 API 응답까지 함께 변경되어야 하는 것은 아니다.

같은 도메인을 표현하고 현재 형태까지 같더라도 API 타입과 프론트엔드 도메인 타입은 목적과 변경되는 이유가 다를 수 있다면 단순히 중복되는 속성을 없애기 위해 두 타입 사이에 불필요한 의존 관계를 만들 필요는 없다고 생각한다.

## 구조적 타이핑을 활용할 수 있다

서로 다른 이유로 변경될 수 있다면 어느 정도의 타입 중복을 감수하고 각각 독립적으로 정의하는 것도 충분한 선택지가 될 수 있다고 생각한다.

TypeScript의 구조적 타이핑을 활용하면 두 타입 사이에 명시적인 관계가 없어도 형태가 호환된다면 그대로 사용할 수 있다.

```ts
interface ProjectResponse {
  id: number;
  name: string;
  description: string;
}

interface Project {
  id: number;
  name: string;
  description: string;
}
```

```ts
const response: ProjectResponse = await getProject();

const project: Project = response;
```

`Project`가 `ProjectResponse`에서 파생된 타입은 아니지만 현재 형태가 같기 때문에 그대로 사용할 수 있다.

이후 두 타입이 각자의 이유로 변화하면서 실제 형태에도 차이가 생긴다면 그때 API와 프론트엔드의 경계에서 차이를 처리하면 된다.

```ts
interface ProjectResponse {
  id: number;
  projectName: string;
  categoryResponses: CategoryResponse[];
}

interface Project {
  id: number;
  name: string;
  categories: Category[];
}
```

```ts
function toProject(response: ProjectResponse): Project {
  return {
    id: response.id,
    name: response.projectName,
    categories: response.categoryResponses,
  };
}
```

결국 타입의 중복을 발견했다고 해서 항상 하나의 타입을 SSOT로 다른 타입을 파생할 필요는 없다고 생각한다.

두 타입이 실제로 함께 변경되어야 하는 관계라면 타입 연산을 통해 그 관계를 표현하고, 서로 다른 이유로 변경될 수 있다면 어느 정도의 중복을 허용하더라도 독립적으로 정의하고 구조적 타이핑을 활용하는 편이 더 자연스러울 수 있다고 생각한다.
