## 모달마다 반환해야 하는 값이 달라졌다

처음에는 `create-folder` 모달만 비동기 방식으로 관리하고 있었다.

폴더 생성이 완료되면 생성된 RoomFolder를 호출한 곳에서 사용해야 했기 때문에, resolve가 전달하는 값과 openModal의 반환 타입을 `RoomFolder | null`로 고정할 수 있었다.

```ts
type GalleryModal = {
  type: "create-folder";
  resolve: (folder: RoomFolder | null) => void;
};

const folder = await openModal({
  type: "create-folder",
});
// RoomFolder | null
```

하지만 다른 모달들도 같은 방식으로 관리하려고 하면서 문제가 생겼다.

`create-folder`는 생성된 폴더 정보가 필요하지만, `delete-folder`는 삭제가 끝났다는 사실만 알면 된다. 앞으로 수정이나 이동과 같은 모달이 추가된다면 각각 필요한 결과도 달라질 수 있다.

결국 다음과 같은 관계가 생긴다.

```text
create-folder → RoomFolder
delete-folder → void
move-media    → ...
```

즉 하나의 `openModal`을 사용하면서도, **어떤 모달을 열었는지에 따라 `resolve`가 전달하는 값과 `openModal`의 반환 타입이 달라져야 했다.**

<br/>

## 결과 타입을 유니온으로 처리하기

가장 먼저 떠오른 방법은 모든 모달의 결과를 하나의 유니온으로 만드는 것이었다.

```ts
type ModalResult = RoomFolder | void;

type GalleryModal = {
  type: "create-folder" | "delete-folder";
  resolve: (result: ModalResult | null) => void;
};

const openModal = (modal: GalleryModalRequest): Promise<ModalResult | null> => {
  // ...
};
```

이렇게 하면 여러 종류의 결과를 하나의 `openModal`에서 처리할 수 있다.

하지만 타입을 살펴보면 아쉬운 점이 있었다.

```ts
const folder = await openModal({
  type: "create-folder",
});

// RoomFolder | void | null
```

나는 분명 `create-folder`를 열었고, 이 비동기가 성공한다면 `RoomFolder`가 반환된다는 것도 알고 있다.

그런데 타입스크립트는 이 정보를 모른다.

```text
create-folder → RoomFolder
delete-folder → void
move-media    → ...
```

정해진 관계가 존재하지만 단순한 유니온은 이를 표현하지 못한다.

`create-folder`를 호출하든 `delete-folder`를 호출하든 항상 모든 결과 타입을 확인해야 했다.

결국 문제는 **여러 결과 타입이 존재한다는 것보다, 모달의 종류와 결과 타입 사이의 관계가 사라진다는 것**이었다.

<br/>

## 관계 표현하기

이 문제를 고민하다가 Item 28에서 API의 경로와 반환 타입을 연결했던 예제가 떠올랐다.

```ts
declare class ApiFetcher<API> {
  fetch<Path extends keyof API>(path: Path): Promise<API[Path]>;
}
```

이 코드에서는 전달된 `Path`를 기준으로 `API[Path]`를 조회해 해당 경로에 맞는 반환 타입을 결정한다.

즉 여러 반환 타입을 하나의 유니온으로 묶는 것이 아니라, **입력으로 들어온 값과 그에 대응하는 결과 타입의 관계를 유지한다.**

모달도 비슷한 관계를 가지고 있었다.

`"create-folder"`를 열었다면 `RoomFolder`가 반환되어야 하고, `"delete-folder"`라면 별도의 결과값이 필요하지 않았다.

그래서 모달과 결과 타입의 관계를 하나의 타입으로 정의했다.

```ts
type GalleryModalResult = {
  "create-folder": RoomFolder;
  "delete-folder": void;
};
```

그리고 `openModal`이 전달받은 type을 제네릭으로 추론한 뒤, 해당 타입을 이용해 결과 타입을 가져오도록 변경했다.

```ts
const openModal = <Type extends keyof GalleryModalResult>(modal: {
  type: Type;
}): Promise<GalleryModalResult[Type] | null> => {
  // ...
};
```

이제 `"create-folder"`를 전달하면 `Type`이 `"create-folder"`로 추론되고, `GalleryModalResult[Type]`은 `RoomFolder`가 된다.

따라서 호출하는 쪽에서도 모달에 맞는 결과 타입을 얻을 수 있다.

```ts
const folder = await openModal({
  type: "create-folder",
});
// RoomFolder | null
```

`resolve` 역시 같은 `GalleryModalResult[Type]`을 사용하도록 만들어, 모달이 내부에서 전달하는 값과 `openModal`이 최종적으로 반환하는 값이 같은 관계를 따르도록 했다.

결과적으로 `type`을 기준으로 **모달 내부의 `resolve`와 외부의 `openModal` 반환 타입을 함께 결정할 수 있게 되었다.**

<br />

## 적용하며 알게 된 점

물론 이번 문제는 Item 28과 완전히 같은 상황은 아니었다.

Item 28에서는 `API`를 먼저 결정하고 이후 함수 호출에서 `Path`를 추론해야 했기 때문에 클래스나 커링을 이용해 제네릭이 결정되는 영역을 나누었다.

반면 현재 코드에서는 `GalleryModalResult`가 이미 정해져 있고, 호출 시 `Type` 하나만 추론하면 되기 때문에 별도의 클래스나 커링까지는 필요하지 않았다.

<br/>

그래도 이번 구현을 통해 Item 28에서의 상황을 조금 더 구체적으로 이해할 수 있었다.

당시 Item 28을 읽을 때는 API의 경로와 반환 타입을 연결하는 예시가 크게 와닿지 않았고, 실제로 이런 방식을 사용할 일이 있을까 싶었다.

하지만 이번에 모달의 `type`과 결과 타입의 관계를 직접 표현해보면서, 당시 예제가 해결하려던 상황을 조금 더 구체적으로 이해할 수 있었다.

제네릭은 단순히 여러 타입을 받을 수 있게 만드는 것뿐만 아니라, **한 타입이 결정되었을 때 관련된 다른 타입도 함께 결정되도록 관계를 유지하는 데 사용할 수 있었다.**
